# PostgreSQL migrations

Target: PostgreSQL 16+. Migrations are append-only and numbered. Never edit an applied migration; add a new migration to change the schema.

## Apply

Use a dedicated migration account, not the runtime API account. Example:

```powershell
$env:PGPASSWORD = "<migration-password>"
psql "host=<vps-host> port=5432 dbname=qr user=qr_migrator sslmode=require" -v ON_ERROR_STOP=1 -f .\migrations\postgresql\0001_initial_schema.sql
Remove-Item Env:PGPASSWORD
```

Do not expose PostgreSQL publicly. Run from a trusted network/VPN or on the VPS itself. Store credentials in a secret manager; the placeholder above is not a real credential.

## Important implementation notes

- The migration creates tenant RLS policies. Before tenant queries, the API must start a transaction and run `SET LOCAL app.current_organization_id = '<validated UUID>'`. The runtime role must not own tables and must not have BYPASSRLS. Migration role should be separate.
- `FORCE ROW LEVEL SECURITY` applies to table owners too, but superusers and BYPASSRLS roles bypass it.
- `users`, `organizations`, `permissions`, `role_permissions`, `owner_feature_policies`, and `audit_events` are central/control-plane or mixed-scope tables and require explicit service authorization. Do not grant broad direct access.
- The application must validate that `parts.kind='assembly'` before writing BOM rows and run a recursive cycle check in the same transaction. A later migration may add a deferred trigger if required; application validation is mandatory.
- UUIDs are generated by the application. This keeps client/server identifiers stable during offline creation.
- `UNLIMITED` means no arbitrary count cap on document versions; it does not mean infinite storage capacity.
- This file has not been executed against a live VPS. Run it first against an empty disposable PostgreSQL 16 database, then run schema, RLS, cross-tenant FK, rollback/restore and migration rehearsal tests before production.


## Authentication bootstrap and tenant context

For the initial organization chooser, the trusted API sets `SET LOCAL app.current_user_id = '<user UUID from the verified session>'` inside a transaction. The memberships RLS policy then exposes only that user's memberships, even before an organization is selected. After the user chooses an organization, the API verifies the active membership and sets `SET LOCAL app.current_organization_id = '<verified organization UUID>'` for tenant queries. Never accept either setting directly from an untrusted request body or let end users connect to PostgreSQL.

Additional RLS policies scope role-permission mappings through tenant roles, license entitlements through tenant licenses, and audit rows to the selected tenant. Platform-wide audit rows require a separate owner-only service context. Global control-plane tables such as owner feature policies remain restricted by database grants and service authorization.

For race-safe BOM edits, the API must acquire the same transaction-scoped advisory lock in a separate SQL command **before** reading or modifying the BOM graph:

```sql
BEGIN;
SELECT pg_advisory_xact_lock(hashtextextended('<validated-organization-uuid>'::text, 0));
-- Read/validate/update BOM only after the lock has been acquired.
COMMIT;
```

The lock must be acquired before the DML statement so that its statement snapshot includes any preceding committed BOM change. Retry the complete transaction on serialization/deadlock errors. The trigger repeats validation as a final database guard; it does not replace this service-level lock ordering.

The migration also enforces:
- current part revision belongs to the same part and organization;
- BOM component revision belongs to the exact component and organization;
- BOM parent is an assembly;
- nested assembly graph is acyclic (serialized per organization with a transaction-scoped advisory lock);
- part revisions, document versions and audit events cannot be updated/deleted in place.

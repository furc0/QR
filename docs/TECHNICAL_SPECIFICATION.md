# QR — Техническое задание
Версия: 0.1  
Статус: архитектурная спецификация, подлежащая уточнению перед реализацией  
Репозиторий: `furc0/QR`

## 1. Назначение проекта

QR — гибридная инженерная платформа для ведения электронного альбома деталей и конструкторской документации. Каждая деталь получает постоянный уникальный идентификатор, человекочитаемый код и защищённую ссылку на карточку. Карточка содержит технические характеристики, изображения, чертежи, документы, 3D-модели и историю изменений.

Система должна работать локально без подключения к интернету и синхронизировать данные с центральным сервером после восстановления соединения. В перспективе одна кодовая база должна поддерживать как приватное использование владельцем, так и коммерческое распространение нескольким организациям.

## 2. Зафиксированные решения

| Область | Решение |
|---|---|
| Тип продукта | Гибридное приложение: desktop/offline-клиент и web-доступ |
| Основной сценарий | Электронный альбом инженерных деталей |
| Доступ | Только аутентифицированным пользователям |
| Офлайн | Полноценное локальное создание, просмотр и редактирование данных |
| Синхронизация | Двусторонняя, после восстановления соединения |
| Лицензирование | Централизованное управление владельцем |
| Ограничения | В первую очередь доступность отдельных функций |
| Дизайн | Modern Technical по умолчанию; сменные темы |
| Распространение | Private сейчас, возможность Commercial в будущем |
| Архитектура | Модульный монолит с чёткими границами модулей |
| Изоляция данных | Поддержка нескольких организаций с первого этапа проектирования |

## 4. Пользователи и модель доступа

### 4.1 Роли

- **Владелец платформы (Platform Owner):** единственный субъект, управляющий глобальными функциями, лицензиями, ключами подписи и политиками распространения.
- **Администратор организации (Organization Admin):** управляет пользователями своей организации и их рабочими ролями; не может изменять глобальную лицензию, тариф, срок действия или глобально запрещённые функции.
- **Конструктор (Designer):** создаёт и редактирует карточки, загружает документацию и модели в рамках выданных разрешений.
- **Инженер (Engineer):** просматривает детали, документы и модели; редактирование — только при наличии соответствующего разрешения.
- **Наблюдатель (Viewer):** просмотр разрешённых данных без изменения.

Роли являются стартовыми шаблонами. Фактический доступ определяется серверной политикой и конкретными разрешениями.

### 4.2 Правила авторизации

- Принцип deny-by-default: доступ запрещён, пока он явно не разрешён.
- Проверка прав выполняется на сервере для каждого защищённого API-действия и операции с файлом.
- Скрытие элемента интерфейса не считается механизмом безопасности.
- Организация пользователя определяется сервером из проверенной сессии, а не из произвольного параметра запроса.
- Все запросы к данным ограничиваются tenant/organization scope.
- Администратор организации не может назначить себе права Platform Owner.
- Критические действия владельца требуют повторной аутентификации и фиксируются в аудите.

## 5. Централизованное управление функциями и лицензиями

### 5.1 Feature Access Control

Ввести централизованный модуль `feature-access`, который вычисляет доступность функции. Для каждой функции задаются стабильный ключ, описание, минимальная версия клиента и правила доступности.

Примеры ключей:

- `catalog.read`
- `catalog.write`
- `documents.upload`
- `documents.export`
- `viewer3d.view`
- `viewer3d.step`
- `sync.cloud`
- `api.integrations`
- `audit.view`
- `admin.users`

Итоговое разрешение должно учитывать глобальную политику владельца, entitlement лицензии организации, роль пользователя и индивидуальные разрешения. Глобальный запрет владельца имеет приоритет над всеми нижестоящими разрешениями. Клиент не может самостоятельно расширить entitlement.

### 5.2 Лицензия и офлайн-разрешение

Центральный сервис лицензирования выпускает криптографически подписанное разрешение (license entitlement/lease), содержащее как минимум:

- ID лицензии и организации;
- список доступных функций;
- дату начала и окончания действия;
- срок допустимой автономной работы;
- идентификатор установки или устройства, если лицензия привязана к устройству;
- версию формата и идентификатор ключа подписи.

Закрытый ключ подписи хранится только в контролируемой владельцем инфраструктуре, предпочтительно в KMS/HSM. В клиентском приложении допускается только открытый ключ проверки подписи.

Клиент проверяет подпись, срок действия и соответствие установки. При подключении он получает актуальную политику и обновлённое разрешение. Подмена локального JSON-файла или изменение интерфейса не должны выдавать доступ к запрещённым серверным функциям.

**Ограничение офлайн-режима:** пока устройство не подключено, невозможно мгновенно доставить отзыв лицензии. Срок офлайн-разрешения определяет максимальный период до обязательной повторной проверки. После истечения периода приложение переходит в заранее определённый безопасный режим: локальное чтение/экспорт данных, если это разрешено политикой, но новые операции с лицензируемыми функциями блокируются. Точный grace period должен задаваться владельцем.

Для полностью автономной установки без внешнего сервера абсолютная защита от владельца локального компьютера невозможна. Если клиент контролирует ОС и исполняемый код, он потенциально может модифицировать клиент. Критичные коммерческие ограничения надёжнее всего обеспечиваются центральным сервисом; офлайн-lease снижает риск, но не делает его нулевым.

### 5.3 Иерархия политик

Приоритет правил:

1. Глобальный запрет Platform Owner.
2. Статус и ограничения лицензии.
3. Разрешения организации.
4. Роль пользователя.
5. Индивидуальные разрешения, если они разрешены политикой владельца.

Каждый результат проверки должен иметь машинно-читаемую причину отказа. Клиенту возвращается только необходимая информация, без раскрытия внутренних секретов и правил подписи.

## 6. Offline-first и синхронизация

### 6.1 Локальный режим

Desktop-клиент хранит рабочие данные в локальной базе SQLite. Файлы размещаются в управляемом локальном хранилище приложения. Данные должны оставаться доступными при отключении сети.

Локальное хранилище должно поддерживать:
- создание и редактирование карточек;
- просмотр уже загруженных документов и моделей;
- добавление файлов;
- поиск и фильтрацию по локальному индексу;
- локальную очередь операций;
- отображение состояния синхронизации;
- безопасное завершение работы при незавершённой синхронизации.

### 6.2 Механизм синхронизации

Использовать transactional outbox/inbox:

1. Локальная операция и запись в outbox фиксируются одной транзакцией.
2. Sync Engine отправляет операции пакетами с уникальными operation ID.
3. Сервер обрабатывает операции идемпотентно.
4. Подтверждённые операции помечаются синхронизированными.
5. Клиент получает изменения сервера через cursor-based pull.
6. Повторная отправка после сбоя не должна создавать дубликаты.

Для файлов использовать контрольные суммы, resumable/chunked upload, проверку типа и размера, антивирусную проверку на серверной стороне при наличии соответствующей инфраструктуры.

### 6.3 Конфликты

Не использовать безусловное правило last-write-wins для инженерных данных.

- Каждая сущность имеет revision/version и updated_at.
- Изменение отправляется с базовой ревизией.
- При несовпадении сервер возвращает конфликт.
- Для карточек создаётся сравнение версий и ручное разрешение конфликта.
- Для неизменяемых файлов создаётся новая версия, прежний файл не перезаписывается.
- Удаление реализуется через tombstone, чтобы удаление корректно распространялось на другие устройства.
- Система сохраняет историю автора и времени изменения.

## 7. Каталог и карточка детали

### 7.1 Идентификаторы

У каждой детали должны быть:
- внутренний неизменяемый UUID;
- уникальный код для человека, например `QR-000001`;
- organization_id;
- статус;
- номер текущей ревизии.

Человекочитаемый код не является секретом и не заменяет проверку доступа. Код не должен переиспользоваться после архивирования или удаления записи.

### 7.2 Поля карточки

Базовые поля:
- наименование;
- обозначение/номер чертежа;
- описание;
- категория и теги;
- материал;
- масса и габаритные размеры;
- единицы измерения;
- производитель/поставщик (опционально);
- статус и ревизия;
- автор и даты создания/изменения;
- связанные детали и сборки;
- список файлов и их версии;
- дополнительные настраиваемые атрибуты.

Схема должна поддерживать расширяемые атрибуты без необходимости менять структуру таблицы при добавлении каждого нового инженерного поля.

### 7.3 QR-коды и ссылки

QR-код содержит непрозрачный URL/токен маршрутизации, а не технические данные и не постоянный секрет доступа. Открытие ссылки всегда приводит к проверке сессии, организации и разрешения на чтение. Публичный доступ по умолчанию выключен.

## 8. Документы и 3D

### 8.1 Документы

Поддержать изображения и распространённые документы: PDF, PNG, JPEG и другие форматы по allowlist. Для каждого файла хранить имя, MIME type, размер, checksum, автора, дату, ревизию и статус проверки.

Загрузка должна проверять расширение, фактический MIME/type, размер и содержимое. Файлы хранить вне web-root, выдавать через контролируемый endpoint или короткоживущие подписанные URL после проверки прав.

### 8.2 3D-модели

Целевые форматы:
- STEP/STP;
- STL;
- OBJ.

Просмотрщик должен поддерживать вращение, панорамирование, масштабирование, стандартные виды, подгонку модели в окно и режимы отображения. Использовать Three.js для визуализации.

STEP не является нативным форматом Three.js. Для него требуется отдельный конвертер на базе OpenCascade (WASM локально или серверный конвертер) с проверкой ресурсов и ограничением времени/памяти. Для offline-first сценария следует исследовать локальную конвертацию STEP в glTF/mesh; исходный STEP хранится без изменений. Выбор конкретного конвертера подтвердить техническим прототипом до фиксации в production.

## 9. Дизайн-система

Стиль по умолчанию — Modern Technical. Внешний вид должен меняться независимо от бизнес-логики.

Требования:
- CSS/design tokens для цветов, типографики, отступов, радиусов, теней и состояний;
- темы как отдельные наборы токенов;
- светлый и тёмный режим;
- смена темы без перезагрузки;
- сохранение предпочтения пользователя;
- компоненты UI не должны содержать бизнес-правила лицензирования;
- доступность интерфейса с клавиатуры и достаточный контраст.

Первые темы: Modern Technical, Industrial Dark, Engineering Professional.

## 10. Предлагаемый технологический стек

Это исходная рекомендация, подлежащая проверке прототипом и анализом поддержки:

- Frontend: React + TypeScript.
- Desktop shell: Tauri 2; локальные системные операции — через минимальный Rust bridge.
- Backend: NestJS + TypeScript, модульный монолит.
- Основная БД сервера: PostgreSQL.
- Локальная БД: SQLite.
- ORM/migrations: Prisma либо другой инструмент, выбранный после проверки поддержки SQLite/PostgreSQL и миграций.
- 3D: Three.js; STEP-конвертация — OpenCascade/WASM или контролируемый backend worker.
- Объектное хранилище: S3-compatible.
- API: REST + OpenAPI; версионирование API обязательно.
- Тесты: unit, integration, end-to-end и security tests.
- Развёртывание сервера: Docker Compose для начального окружения; production-конфигурация отдельно.

Не начинать с микросервисов. Модульный монолит проще тестировать и развёртывать; выделение сервисов допускается только при доказанной необходимости.

## 12. Базовые требования безопасности

1. TLS для всех сетевых соединений.
2. Пароли не хранить в открытом виде; использовать современный password hashing (Argon2id предпочтительно).
3. Секреты не включать в исходный код, клиентские сборки, Git или логи.
4. Сессии — защищённые, с ротацией и отзывом; cookies с HttpOnly, Secure и подходящим SameSite для web-клиента.
5. MFA для Platform Owner обязательно; повторная аутентификация для критических действий.
6. Проверка авторизации на каждом серверном endpoint и при каждом доступе к файлу.
7. Защита от CSRF, XSS, SQL injection, SSRF, path traversal и небезопасной десериализации.
8. Ограничение частоты запросов, размера загрузок и времени тяжёлых операций.
9. Изоляция tenant-данных на уровне сервисов и БД; тесты на межорганизационный доступ.
10. Подписанные лицензии и проверка подписи на клиенте; закрытый ключ не поставляется клиенту.
11. Шифрование резервных копий и защита ключей шифрования.
12. Аудит входов, изменения политик, управления пользователями, экспорта и удаления данных.
13. Подписание релизов и проверка целостности обновлений.
14. Регулярное обновление зависимостей, secret scanning, dependency scanning и анализ уязвимостей.
15. План реагирования на компрометацию ключа, отзыв лицензий, восстановление резервных копий и инциденты.

## 13. Нефункциональные требования

- Локальный просмотр ранее загруженных данных не зависит от доступности сервера.
- После восстановления соединения синхронизация продолжается автоматически и безопасно после перезапуска приложения.
- Повторные запросы синхронизации идемпотентны.
- Ни одна организация не может читать данные другой организации.
- Запрещённая функция недоступна через API, даже если клиент модифицирован.
- Изменения карточек и файлов имеют историю.
- Резервная копия должна быть проверяема восстановлением, а не только фактом успешного создания.
- Интерфейс должен масштабироваться на desktop и tablet.
- Смена темы не меняет поведение и права доступа.
- Все критические ошибки синхронизации должны быть видны пользователю и доступны в диагностическом журнале без утечки секретов.

## 14. Критерии приёмки

Первая версия не считается готовой, пока не выполнены следующие проверки:

1. Пользователь без сессии не может открыть защищённую карточку или файл.
2. Пользователь одной организации не может получить данные другой организации подменой ID.
3. Отключение интернета не мешает создавать и редактировать локальные карточки.
4. После восстановления соединения изменения синхронизируются без дубликатов.
5. Конфликт двух редакторов обнаруживается и не приводит к молчаливой потере данных.
6. Повреждённая или изменённая лицензия не проходит криптографическую проверку.
7. Отключённая владельцем функция недоступна через прямой API-запрос.
8. Администратор организации не может изменить глобальную политику или лицензию.
9. Истёкшее офлайн-разрешение приводит к предусмотренному политикой режиму, а не к неограниченному доступу.
10. QR-ссылка не даёт анонимного доступа к данным.
11. Смена темы не меняет бизнес-логику.
12. Резервная копия успешно восстанавливается в тестовом окружении.
13. STEP/STP, STL и OBJ проходят отдельные тесты импорта/просмотра; ограничения STEP-конвертации документированы.

## 17. Утверждённые уточнения от 2026-11-25

Следующие решения заменяют соответствующие открытые вопросы разделов 15–16 и являются обязательными для проектирования MVP.

| Область | Утверждённое решение |
|---|---|
| Целевая ОС desktop-клиента | Windows — первая и приоритетная платформа |
| Центральная инфраструктура | VPS под контролем владельца платформы |
| Offline lease | Настраиваемый владельцем срок и режим |
| Поведение после истечения lease | Полная блокировка рабочего приложения до восстановления действительного разрешения |
| Локальное шифрование | Обязательно: база данных и локальные файлы |

### 17.1 Windows-first

Первая поставляемая desktop-сборка ориентирована на Windows 10/11 x64. Архитектура не должна искусственно привязывать доменную логику к Windows API: платформенные операции изолируются в адаптерах, чтобы в будущем можно было добавить другие ОС.

### 17.2 VPS

Центральный API, PostgreSQL, сервис лицензирования, аудит и объектное хранилище размещаются на VPS под административным контролем владельца. Production-развёртывание должно включать TLS, firewall с минимально открытыми портами, отдельные учётные записи сервисов, автоматические обновления безопасности ОС, мониторинг, резервные копии и проверку восстановления. База данных и административные интерфейсы не должны быть открыты напрямую в интернет.

### 17.3 Настраиваемый offline lease

Владелец задаёт срок автономной работы и связанные параметры политики через защищённую панель управления. Значение не зашивается в клиентскую сборку. Клиент получает подписанный lease от центрального сервиса и проверяет его локально. Изменение системных часов рассматривается как попытка обхода: клиент использует защищённое хранение последнего достоверного времени/состояния и обнаруживает существенный откат часов. Это повышает устойчивость, но не даёт абсолютной гарантии на полностью контролируемом пользователем устройстве.

### 17.4 Полная блокировка после истечения lease

После истечения lease приложение блокирует рабочие функции и не выполняет новые операции с данными до получения действительного разрешения от центрального сервиса. Допускается только ограниченный экран восстановления лицензии/подключения и диагностики, не раскрывающий данные деталей.

Локальные данные и неподтверждённые операции синхронизации не удаляются и не повреждаются при блокировке. После восстановления лицензии приложение продолжает синхронизацию. Это предотвращает потерю инженерной работы, но не предоставляет пользователю обходной режим доступа к защищённым функциям.

### 17.5 Шифрование локальных данных

Локальная база должна использовать шифрование на уровне базы (например, SQLCipher или эквивалент, выбранный после проверки совместимости с выбранным SQLite-драйвером). Локальные документы и модели должны шифроваться с использованием аутентифицированного шифрования (например, AES-256-GCM) с уникальными nonce и проверкой целостности.

Ключи шифрования не хранятся рядом с зашифрованными данными в открытом виде. Для Windows предпочтительно защищать ключ материала через DPAPI в контексте учётной записи пользователя; при наличии подходящего оборудования можно дополнительно использовать TPM. Не хранить ключи, пароли или lease secrets в репозитории, логах или открытом конфигурационном файле.

Обязательно предусмотреть документированную процедуру восстановления/переноса данных. Потеря Windows-профиля или ключа не должна неожиданно приводить к необратимой потере единственной копии инженерных данных; резервные копии шифруются отдельно и проверяются восстановлением.

### 17.6 Обновлённые критерии приёмки

14. Первая desktop-сборка устанавливается и запускается на поддерживаемой Windows 10/11 x64.
15. При отсутствии сети пользователь может выполнять предусмотренные offline-операции в пределах действующего lease.
16. Срок lease настраивается владельцем и проверяется клиентом по подписанному разрешению.
17. После истечения lease рабочее приложение блокируется; локальные данные и outbox сохраняются без повреждения.
18. После восстановления соединения и выдачи действительного lease приложение разблокируется и продолжает синхронизацию.
19. Содержимое локальной БД и файлового хранилища не читается как открытый текст при исследовании файлов на диске без соответствующих ключей.
20. Резервная копия локальных данных может быть восстановлена по предусмотренной процедуре с проверкой целостности.


## 18. Утверждённая модель данных от 2026-11-25

Ниже приведённые решения являются окончательными для первой реализации и заменяют соответствующие вопросы о модели данных в предыдущих разделах.

| Решение | Утверждённое значение |
|---|---|
| Уникальность кода детали | Внутри организации: `UNIQUE(organization_id, part_code)` |
| Несколько организаций у пользователя | Да; отдельное членство и набор ролей в каждой организации |
| Сборки и спецификации | Да; сборка — вид детали, состав хранится как BOM |
| История файлов | Без искусственного лимита количества версий; новые загрузки создают новые неизменяемые версии |

### 18.1 Сборки и спецификации

Деталь имеет тип `part` или `assembly`. Сборка содержит строки BOM: компонент, количество, единица измерения, позиция/номер позиции, примечание и необязательная ссылка на конкретную ревизию компонента. Вложенные сборки поддерживаются. Backend обязан запрещать циклический состав и проверять тип родительского объекта до публикации спецификации.

### 18.2 Версии документов

Документ является логической записью, а бинарные загрузки представлены отдельными неизменяемыми версиями. Обновление файла создаёт следующую версию и не перезаписывает предыдущую. Прикладного лимита количества версий нет. Физическое удаление регулируется отдельной административной процедурой, резервным копированием и требованиями хранения; оно не является обычным редактированием.

### 18.3 Миграции и база данных

Первая серверная миграция находится в `migrations/postgresql/0001_initial_schema.sql`, локальная схема — в `migrations/sqlite/0001_local_schema.sql`. Они являются стартовыми схемами для новой базы, а не миграцией существующих пользовательских данных. Перед production применением обязательны тестовый прогон PostgreSQL 16+, проверка RLS, межорганизационных ограничений, backup/restore и SQLCipher driver compatibility. Применённые миграции не редактируются; все последующие изменения добавляются новыми файлами.

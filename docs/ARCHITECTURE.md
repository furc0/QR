# QR — Архитектура системы
Версия: 0.1  
Статус: проект архитектуры для реализации MVP  
Связанный документ: TECHNICAL_SPECIFICATION.md

## 1. Архитектурные цели

Архитектура QR должна одновременно обеспечить:

- Windows-first desktop-клиент с полноценной offline-first работой.
- Центральный VPS, контролируемый Platform Owner.
- Централизованное управление лицензиями и доступностью функций.
- Защиту данных организаций друг от друга.
- Смену дизайна без изменения бизнес-логики.
- Возможность будущего коммерческого multi-tenant распространения.
- Управляемую сложность: модульный монолит вместо преждевременного набора микросервисов.

Ключевой принцип: клиент хранит локальную рабочую копию данных, но не является источником истины для лицензий, глобальных политик и серверных прав доступа.

## 2. Контекст и границы доверия

### 2.1 Контекст системы

Пользователь работает в QR Desktop под Windows. Клиент хранит локальную зашифрованную БД и файлы. При наличии сети он взаимодействует по TLS с QR API на VPS. API обращается к PostgreSQL, приватному объектному хранилищу, License & Policy Engine и Audit Log. Platform Owner управляет глобальными настройками через отдельную защищённую административную зону.

### 2.2 Границы доверия

1. **Desktop-клиент:** считается потенциально модифицируемой средой. Локальные проверки повышают устойчивость и обеспечивают offline UX, но не заменяют серверную авторизацию.
2. **VPS API:** доверенная серверная зона под управлением владельца. Все входящие данные считаются недоверенными и валидируются.
3. **PostgreSQL:** недоступен напрямую из публичного интернета; доступен только серверным сервисам с минимальными правами.
4. **Object Storage:** приватное хранилище. Все выдачи объектов проходят авторизацию или используют короткоживущие URL после проверки прав.
5. **Owner Control Plane:** особо защищённая зона; MFA обязательно, повторная аутентификация для критических действий.
6. **Signing Keys:** закрытые ключи лицензирования не находятся в desktop-клиенте, Git или обычной конфигурации приложения.

## 3. Логическая архитектура

### 3.1 Desktop-клиент

Рекомендуемая оболочка — Tauri 2 с React/TypeScript UI и минимальным Rust bridge. Desktop разделён на следующие части:

- **Presentation:** страницы, компоненты, темы, состояния интерфейса.
- **Application:** сценарии пользователя (создать деталь, добавить файл, синхронизировать).
- **Domain:** правила карточек, ревизий, разрешений и конфликтов.
- **Local Infrastructure:** SQLite, локальные файлы, криптография, outbox/inbox.
- **Platform Adapter:** Windows DPAPI, системное хранилище, установщик и обновление.

UI не должен самостоятельно решать, разрешена ли операция. Он запрашивает результат у application/domain слоя, а серверные операции дополнительно проверяются API.

### 3.2 Центральный backend

Backend — модульный монолит NestJS. Модули имеют собственные сервисы и границы ответственности, взаимодействуют через публичные интерфейсы и события приложения.

| Модуль | Ответственность |
|---|---|
| Identity & Auth | Пользователи, сессии, MFA |
| Organizations | Организации, членство и tenant context |
| Authorization | Роли и проверка разрешений |
| Feature Access | Эффективный набор доступных функций |
| Licensing | Выпуск, продление и отзыв лицензий/lease |
| Catalog | Детали, атрибуты, категории, связи |
| Documents | Метаданные, версии и безопасная выдача файлов |
| QR Generator | Формирование QR-маршрутов |
| Sync | Приём локальных операций, pull changes, конфликты |
| Audit | Неизменяемый журнал значимых событий |
| Owner Control Plane | Глобальные настройки, функции и лицензии |

Модульный монолит должен иметь возможность позже вынести тяжёлые задачи (например, STEP-конвертацию) в отдельный worker, не превращая все модули в сетевые сервисы заранее.

## 4. Развёртывание VPS

### 4.1 Компоненты

- Reverse proxy / TLS termination.
- API application.
- PostgreSQL.
- Приватное S3-compatible object storage или внешний приватный bucket.
- Background worker для тяжёлых/асинхронных задач.
- Мониторинг, сбор метрик и централизованные логи.
- Сервис резервного копирования.

### 4.2 Сетевая модель

- Публично доступны только HTTPS endpoint и необходимые endpoints обновления, если они будут добавлены.
- PostgreSQL, внутренние панели и storage management не публикуются напрямую.
- Межсервисные подключения ограничены firewall/security groups.
- Административный SSH — по ключам, с ограничением источников доступа и без password login, если это совместимо с операционной процедурой владельца.
- Секреты предоставляются через защищённое хранилище/переменные окружения deployment-среды, не коммитятся в репозиторий.

### 4.3 Резервное копирование

- PostgreSQL: регулярные encrypted backups и, при необходимости, WAL/PITR.
- Object storage: versioning и независимая резервная копия.
- Ключи шифрования и подписи резервируются отдельно с контролем доступа.
- Регулярные тестовые восстановления в изолированной среде.
- Владелец задаёт RPO/RTO после оценки объёма данных и стоимости инфраструктуры.

## 5. Локальная архитектура и шифрование

### 5.1 Хранилище

Локально используются:
- SQLite с шифрованием на уровне БД (SQLCipher или совместимый проверенный вариант).
- Файловое хранилище, содержащее зашифрованные объекты.
- Таблицы outbox/inbox, cursor sync и локального состояния лицензии.
- Локальный поисковый индекс, который можно восстановить из данных.

### 5.2 Управление ключами

1. Генерируется случайный data encryption key для локального хранилища.
2. База и файлы шифруются отдельными ключами/контекстами с аутентифицированным шифрованием.
3. Ключевой материал защищается Windows DPAPI в контексте пользователя; возможность TPM-backed защиты оценивается отдельно.
4. Ключи не записываются в логи и не передаются серверу как открытые секреты.
5. Резервная копия использует отдельный механизм envelope encryption и документированную процедуру восстановления.

DPAPI привязывает защиту к Windows-профилю/контексту. Поэтому перенос данных на другой компьютер требует предусмотренного экспорта/восстановления, а не простого копирования каталога приложения.

### 5.3 Защита локальных файлов

Файлы шифруются до записи в управляемое хранилище. Метаданные содержат алгоритм/версию формата, nonce, tag, размер и checksum ciphertext. Для AES-GCM запрещено повторное использование nonce с одним ключом. Оригинальные файлы не модифицируются в процессе импорта; сохраняются checksum исходника и метаданные версии.

## 6. Лицензирование и Feature Access

### 6.1 Центр принятия решений

Серверный License & Policy Engine формирует effective entitlements. Desktop получает подписанный lease с набором функций и временными границами. API самостоятельно проверяет действующие права при каждом защищённом действии.

### 6.2 Подписанный lease

Предлагаемый формат — versioned JSON payload с цифровой подписью Ed25519 или другой алгоритм, утверждённый после криптографического review. Подписывается точное каноническое представление payload. Клиент содержит только публичные ключи и поддерживает key ID для ротации.

Payload включает:
- lease_id;
- license_id;
- organization_id;
- installation_id (если требуется привязка);
- issued_at, not_before, expires_at;
- offline_until;
- features/entitlements;
- policy_version;
- signing_key_id;
- schema_version.

Секретный signing key хранится в KMS/HSM или эквивалентной защищённой среде. Не помещать приватный ключ в клиент, Docker image, репозиторий или обычный .env-файл.

### 6.3 Настраиваемый период offline lease

Platform Owner задаёт продолжительность автономного периода. Сервер выпускает lease с соответствующим offline_until. Изменение глобальной политики применяется при следующем успешном соединении. Мгновенно отозвать offline lease на отключённом устройстве технически невозможно.

### 6.4 Истечение lease

После наступления offline_until desktop:
- блокирует рабочее пространство и защищённые операции;
- показывает только экран подключения/восстановления лицензии;
- сохраняет зашифрованную локальную БД, файлы и outbox;
- не удаляет локальные данные;
- возобновляет работу только после проверки нового действительного lease.

Состояние блокировки должно быть единым для всех окон/процессов клиента. Перезапуск не должен сбрасывать срок или обходить блокировку.

### 6.5 Авторизация каждой операции

Проверка UI — только подсказка. Для API операция проходит:
1. проверку действительной сессии;
2. определение tenant из проверенного контекста;
3. проверку членства пользователя в tenant;
4. проверку entitlement функции;
5. проверку role/permission;
6. проверку доступа к конкретному объекту;
7. выполнение операции;
8. аудит критичного действия.

Нельзя доверять organization_id, feature flags, роли или цене/тарифу, присланным клиентом без серверной проверки.

## 7. Offline-first и Sync Engine

### 7.1 Локальная запись

Команда пользователя сохраняет изменения доменной сущности и запись outbox в одной локальной транзакции. Операция содержит operation_id, entity_id, entity_type, base_revision, actor/device context, operation payload и локальную временную метку.

### 7.2 Push

- Клиент отправляет пакет операций с idempotency keys.
- Сервер проверяет lease/session/tenant и допустимость каждой операции.
- Сервер хранит обработанные operation_id, чтобы повтор не создавал дубликат.
- Сервер фиксирует доменные изменения и audit events транзакционно там, где это возможно.
- Конфликт возвращается явно, без автоматического затирания.

### 7.3 Pull

Клиент получает изменения после сохранённого server cursor. Cursor обновляется только после надёжного применения пакета локально. Повторная доставка безопасна. Tombstones распространяют удаления.

### 7.4 Конфликты

Для инженерных карточек используется optimistic concurrency control по revision. При конфликте создаётся локальная ветка/копия изменения для сравнения. Пользователь выбирает, какие поля принять, либо сохраняет изменение как новую ревизию. Для бинарных документов конфликт разрешается созданием отдельной версии, а не объединением содержимого.

### 7.5 Поведение при сбоях

- Сбой сети не теряет outbox.
- Сбой приложения не оставляет частично применённую локальную транзакцию.
- Повтор push не создаёт дубликаты.
- Ошибка одного элемента пакета не должна бесследно терять остальные операции; политика batch processing документируется и тестируется.
- Повреждённый файл помещается в карантин и не открывается как доверенный документ.

## 9. QR-маршруты

QR-код не хранит карточку и не является разрешением доступа. Он содержит маршрут к детали с непрозрачным идентификатором. Маршрут разрешается через API, после чего пользователь проходит аутентификацию и проверку tenant/object permissions. Секретные токены доступа не должны быть постоянными QR-значениями. Отзыв/перевыпуск маршрута не должен менять внутренний ID детали.

## 10. UI и дизайн-система

UI организован в отдельном пакете. Бизнес-компоненты не содержат жёстко заданные цвета и оформление; используют семантические design tokens.

Темы:
- Modern Technical — default;
- Industrial Dark;
- Engineering Professional.

Настройки темы локальны для пользователя/устройства и могут синхронизироваться как preference. Смена темы не влияет на feature entitlements или доступ к данным.

## 11. Наблюдаемость и аудит

Логи не должны содержать пароли, токены, ключи, содержимое чертежей или приватные данные карточек без необходимости. Структурированные события включают correlation_id, actor_id, organization_id, operation, outcome и timestamp.

Обязательные аудит-события:
- вход, выход, MFA и неудачные попытки;
- выдача/продление/отзыв лицензии;
- изменение глобальной политики и функций;
- изменение пользователей и ролей;
- создание/изменение/архивирование деталей;
- загрузка, скачивание и экспорт файлов;
- конфликт и результат его разрешения;
- действия восстановления и резервного копирования.

Журнал аудита должен быть append-oriented, а права на изменение/удаление событий — отделены от обычных административных прав.

## 12. Проверки архитектуры и безопасности

Минимальный набор автоматизированных проверок:

- tenant isolation: попытки чтения/изменения объектов другой организации;
- authorization matrix: каждая роль × каждая защищённая операция;
- feature denial: прямой API-вызов запрещённой функции;
- lease: неверная подпись, истечение, другой installation_id, key rotation, clock rollback;
- offline: отсутствие сети, перезапуск, повторная отправка, конфликт, восстановление;
- encryption: данные на диске не содержат открытые документы/записи; неправильный ключ и повреждённый ciphertext отклоняются;
- file upload: подмена MIME, двойные расширения, чрезмерный размер, path traversal, вредоносные/повреждённые файлы;
- backup: восстановление БД, объектов и ключевого материала в изолированную среду;
- desktop: блокировка lease действует после перезапуска и во всех окнах.

## 13. Открытые архитектурные решения

До фиксации схемы и кода требуется техническая проверка:

1. Совместимость Tauri 2, выбранного SQLite/SQLCipher binding и Windows DPAPI.
2. Сравнение вариантов object storage для VPS и стоимости резервного копирования.
3. STEP/STP pipeline: OpenCascade WASM локально против backend worker; оценить большие файлы, память, время и качество tessellation.
4. Механизм защищённого хранения signing keys на VPS (KMS/HSM или эквивалент).
5. Точные RPO/RTO, максимальный размер файла и лимиты каталога.
6. Правила восстановления ключа локального хранилища при переустановке Windows или переносе на другой компьютер.

Эти вопросы решаются короткими техническими spike/prototype, а не догадками в production-коде.

## 14. Порядок реализации

1. Зафиксировать data model и permission matrix.
2. Поднять monorepo, CI, форматирование, линтеры и тестовый контур.
3. Реализовать backend identity, organizations и authorization.
4. Реализовать owner control plane, feature policy и license signing.
5. Реализовать catalog и document metadata/API.
6. Создать Windows desktop shell и encrypted local storage.
7. Реализовать outbox/inbox sync и конфликт-менеджмент.
8. Добавить QR маршруты и 3D viewer.
9. Выполнить security tests, backup/restore и deployment hardening.

Не переходить к широкому UI/функционалу до проверки tenant isolation, permission enforcement и локального шифрования.
